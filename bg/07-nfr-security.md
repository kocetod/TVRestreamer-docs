## 2. Капацитетно планиране (2 500 абоната)

**Допускания:** пикова едновременност 60% → **1 500 зрители**; среден битрейт 4 Mbps (микс SD/HD/FHD); 300 канала; 30% от каналите с hot standby.

| Ресурс | Изчисление | Резултат |
|---|---|---|
| Изходящ трафик (пик) | 1 500 × 4 Mbps | **6 Gbps** (+30% запас → 8 Gbps) |
| Входящ трафик (ingest) | 300 × 5 Mbps × 1,3 | **≈ 2 Gbps** |
| CPU ingest | 300 × (1 input + 1 packager) × ~1,5% ядро + 90 standby × 1% | **≈ 10 ядра** |
| tmpfs за HLS | 300 × 8 сегм. × 4 сек × 5 Mbps / 8 | **≈ 6 GB** |
| Redis | 2 000 сесии × ~1 KB | < 50 MB |
| PostgreSQL | Сесии 90 дни ≈ 5 млн реда | ≈ 5 GB |

### Препоръчан хардуер (старт)

| Роля | Брой | Спецификация |
|---|---|---|
| Control plane (core, PG, Redis, Grafana) | 1 (+1 standby в R2) | 4–8 vCPU, 16 GB RAM, 200 GB NVMe |
| Ingest | 2 (активен + резервен, или 2 × 150 канала) | 16 ядра, 64 GB RAM, 2 × 10 Gbps, Ubuntu 24.04 |
| Edge | 2–3 (N+1) | 8 ядра, 32 GB RAM, 1–2 × 10 Gbps (или 25 Gbps) |

> За старта е възможна и конфигурация **ALL_IN_ONE** на 1–2 мощни сървъра (32 ядра, 128 GB, 2 × 10G). Ролите се разделят по-късно без промяна в кода.

## 3. Сигурност

### 3.1 Модел на заплахите (STRIDE, накратко)

| Заплаха | Пример | Мярка |
|---|---|---|
| **S**poofing | Кражба на админ парола | 2FA за Admin, заключване след 5 опита, админ панел само от разрешени IP/VPN |
| **S**poofing | Споделяне на абонатски линк | Лимит на сесиите, кратки подписани URL на сегментите, регенериране на токена, IP binding (опц.) |
| **T**ampering | Подправяне на сегмент URL | HMAC-SHA256 подпис с изтичане (njs на edge, TVR-044) |
| **R**epudiation | „Не съм го изтрил аз“ | Одит лог с diff, append-only |
| **I**nformation disclosure | Изтичане на URL на доставчиците | URL-ите на източниците не се показват на абонатите; шифриране на тайните в БД; роля Support не вижда входове |
| **D**enial of service | Флууд на `/internal/auth` или плейлисти | Rate limit на nginx (`limit_req`), кеш на auth 10 сек, fail2ban по 403 |
| **E**levation of privilege | Support прави промени като Admin | RBAC на ниво API (Spring Security `@PreAuthorize`), тестове за всяка роля |

### 3.2 Изисквания за сигурност

| ID | Изискване |
|---|---|
| SEC-01 | TLS 1.2+ навсякъде публично (Let's Encrypt/ACME); HSTS на админ домейна |
| SEC-02 | mTLS между core и агентите; сертификат на агент се отнема при премахване на node |
| SEC-03 | Пароли с Argon2id; API ключовете се пазят само като hash (показват се веднъж) |
| SEC-04 | JWT access 15 мин, refresh 7 дни с ротация; refresh в httpOnly, Secure, SameSite=Strict cookie |
| SEC-05 | Тайни (пароли на източници, SRT passphrase, ключ за подписване) — AES-256-GCM, ключът от env/secret файл, не в git |
| SEC-06 | Валидиране на всички входове (Bean Validation). FFmpeg командите се строят като **списък аргументи**, никога чрез shell, за защита от command injection чрез URL |
| SEC-07 | Ограничение на позволените схеми в URL на входовете (`http, https, udp, rtp, srt, rtmp, rtsp`). Забранени са `file:`, `concat:`, `subfile:` и т.н. (защита от четене на локални файлове чрез FFmpeg) |
| SEC-08 | Security headers в UI (CSP, X-Frame-Options, Referrer-Policy) |
| SEC-09 | Зависимости: OWASP Dependency-Check / Renovate в CI; Trivy сканиране на образите |
| SEC-10 | Агентът работи като непривилегирован потребител `tvr`; FFmpeg с ограничения (systemd `ProtectSystem`, `NoNewPrivileges`) |
| SEC-11 | Бекъпите са шифрирани и се пазят извън сървъра |
| SEC-12 | Логовете не съдържат пароли, токени (маскиране `tok_****abcd`) и пълни URL с credentials |
