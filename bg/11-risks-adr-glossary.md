## 2. Архитектурни решения (ADR)

### ADR-001 · FFmpeg за медийния I/O, Java за логиката
- **Контекст:** Нужна е поддръжка на много протоколи (HTTP, HLS, UDP, SRT, RTMP, RTSP) и стабилно HLS пакетиране.
- **Решение:** FFmpeg процеси (`-c copy`), управлявани от Java агент. Видеото не минава през JVM, освен TS превключвателя (виж ADR-003).
- **Последствия:** + зрял и бърз I/O, + лесен дебъг (командата може да се пусне ръчно); − по 1–2 процеса на канал, нужно е добро супервизиране.

### ADR-002 · Java 21 + Spring Boot 3 за core и агента
- **Контекст:** Изборът на собственика. Нужни са REST, сигурност, ORM, gRPC, метрики.
- **Решение:** Spring Boot 3.3 (заменено с 4.1 — виж ADR-010), virtual threads за блокиращ I/O, Netty за TS пътя.
- **Последствия:** + един език в бекенда, богат екосистем; − по-висока RAM от Go (приемливо).

### ADR-003 · Собствен TS превключвател и анализатор (Netty)
- **Контекст:** Рестартът на FFmpeg при failover дава прекъсване от 5–10 сек и „чупи“ HLS.
- **Решение:** Входовете пращат TS по UDP loopback към агента. Агентът избира активния вход, анализира пакетите (PAT/PMT/CC/PCR) и препраща към packager-а.
- **Последствия:** + failover < 3 сек, + Astra-подобен анализатор „безплатно“; − собствен код за MPEG-TS (покрива се с property-based тестове); − допълнително копиране през loopback (пренебрежимо: ~5 Mbps на канал).

### ADR-004 · HLS като основен изход, сервиран от nginx
- **Контекст:** 2 000 зрители, ~6–8 Gbps.
- **Решение:** FFmpeg пише HLS в tmpfs, nginx origin + nginx edge с `proxy_cache_lock`. HTTP-TS се раздава от Netty relay в агента, проксиран от edge.
- **Последствия:** + nginx е най-ефективният файлов сървър (sendfile), + edge се мащабира хоризонтално; − HLS добавя 10–20 сек латентност (приемливо за IPTV).

### ADR-005 · Авторизация: `auth_request` за плейлиста, `secure_link` за сегментите
- **Контекст:** ~375 заявки/сек за плейлисти и ~1 500 за сегменти при пик; core не трябва да е в горещия път.
- **Решение:** Само заявката за плейлист минава през core (с кеш 10 сек на edge). Сегментите се проверяват локално с HMAC.
- **Последствия:** + core обработва < 400 RPS, + edge работи и при кратко отпадане на core; − отнемането на достъп има закъснение ≤ 10 сек (кеш) + 60 сек (живот на подписа).
- **Реализация (TVR-044):** подписът е HMAC-SHA256 в njs (създава се в плейлиста, проверява се за всеки сегмент), а не `secure_link_md5` — вграденият модул поддържа само MD5. Принципът (локална проверка без core) е същият.

### ADR-006 · Desired state + reconciliation между core и агент
- **Решение:** Core изпраща пълен snapshot с версия. Агентът е идемпотентен.
- **Последствия:** + устойчивост на загубени съобщения и рестарти; − по-голям payload (несъществено при < 500 канала).

### ADR-007 · Docker Compose + Ansible вместо Kubernetes
- **Решение:** Малък брой сървъри (3–6), нужен е host networking и multicast.
- **Последствия:** + проста експлоатация; − ръчно мащабиране (приемливо).

### ADR-008 · Без прекодиране до R3
- **Решение:** Само `-c copy`. Транскодирането се добавя като отделен тип „processing profile“ с GPU.
- **Последствия:** + евтин хардуер, ниска латентност; − каналите се раздават с оригиналния битрейт и кодек.

### ADR-009 · Gradle вместо Maven
- **Контекст:** Собственикът вече има Gradle проект в IntelliJ.
- **Решение:** Gradle multi-project (tvr-common, tvr-core, tvr-agent) с version catalog.
- **Последствия:** + без смяна на инструмента; + по-бърз инкрементален build; − малко по-различни конвенции от Maven (несъществено).

### ADR-010 · Spring Boot 4.1 вместо 3.3
- **Контекст:** Spring Boot 3.3 и 3.5 вече са извън безплатната (OSS) поддръжка (3.5 — от 30.06.2026). Актуалната линия е 4.1 (4.1.1, август 2026).
- **Решение:** tvr-core и tvr-agent ползват Spring Boot 4.1.x (Spring Framework 7, Jakarta EE 11, JUnit 6, Testcontainers 2). Версията е на едно място: `gradle/libs.versions.toml`.
- **Последствия:** + поддръжка и security поправки; + вградени структурирани (JSON) логове; − нови имена на някои starters (напр. `spring-boot-starter-webmvc`) и Jackson 3 — примерите в интернет за Boot 3 не винаги важат.

## 3. Речник

| Термин | Значение |
|---|---|
| **Restream** | Препредаване на поток от източник към много зрители, без промяна на съдържанието |
| **Ingest** | Приемане на входящия поток |
| **Edge** | Сървър, който раздава съдържанието на крайните зрители |
| **Origin** | Сървър, от който edge взема съдържанието |
| **MPEG-TS (TS)** | Transport Stream — контейнерът, използван в телевизията (188-байтови пакети) |
| **SPTS / MPTS** | Single/Multi Program Transport Stream — един или много канали в един поток |
| **PID** | Packet Identifier — идентификатор на елементарен поток в TS |
| **PAT / PMT / SDT** | Таблици в TS: списък на програмите, PID-ове на програма, имена на услугите |
| **PNR** | Program Number (service ID) |
| **CC грешка** | Continuity Counter error — изгубен или повторен TS пакет |
| **PCR** | Program Clock Reference — часовникът на потока |
| **Scrambled** | Шифрован (кодиран) поток |
| **HLS** | HTTP Live Streaming — плейлист `.m3u8` + сегменти `.ts`/`.m4s` |
| **HTTP-TS** | Непрекъснат MPEG-TS по HTTP връзка |
| **SRT** | Secure Reliable Transport — протокол за надежден пренос през интернет |
| **Multicast / IGMP** | Едно-към-много пренос в локална мрежа / протокол за абониране |
| **Failover** | Автоматично превключване към резервен източник |
| **Hot standby** | Резервният източник е постоянно приет и готов за мигновено превключване |
| **LCN** | Logical Channel Number — номер на канала в списъка |
| **EPG / XMLTV** | Електронен програмен справочник / формат за него |
| **M3U** | Формат на плейлист за IPTV плейъри |
| **Xtream Codes API** | De-facto стандарт за IPTV панели, поддържан от повечето плейъри |
| **Slate** | Резервна картина при липса на сигнал |
| **Middleware** | Система за управление на абонати и достъп |
| **Desired state** | Описание на желаното състояние, към което системата се стреми сама |
